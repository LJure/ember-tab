## 修改及原因

### 备份与恢复

- 保持 Aura 的 `aura-tab-webdav-backup` / schemaVersion 1、存储键和数据库名称，未引入不兼容的新备份格式。
- 修复导出 Blob 文件名碰撞：不同图标键经过路径字符替换／截断后可能变成相同 ZIP 路径；现在加记录序号。测试使用 `m4/a` 与 `m4:a` 复现旧导出器的问题。已产生重复路径的历史包会明确拒绝，不能凭空找回其中丢失的图片。
- 恢复先解压到 staging 并检查结构、必需记录、唯一 ID、Blob 引用和声明大小，再修改正式数据。拒绝不安全路径、重复路径、超量条目、缺失必需条目及超出 Sync 配额的包。
- 恢复前检查新旧 Sync 键的合并峰值，避免先写后删期间超配额。即使最终状态能放下，合并峰值过大也会保守拒绝；不会通过提前清空现有数据来腾空间。
- 图片先恢复，存储元数据随后发布，避免页面监听器把尚未导入的图片清理掉。每个 IndexedDB store 使用一个事务清空和写回，等待事务完成；中止或磁盘错误返回失败。
- 跨页面恢复通过 Web Locks 串行化，同时与快捷链接写入共用锁。可选旧缓存中不兼容的记录会计数，界面提示“已恢复，但部分旧缓存未导入”。保留当前 WebDAV 配置；备份不导出该配置。
- 真实导出错误不再伪装成空的可选缓存。OPFS 获取目录／创建写入器失败时清理临时文件，并回退到有容量限制的内存导出。流式压缩等待磁盘写入，避免写入队列不断积累。

### Sync、并发与启动

- 快捷链接读取使用同一次存储快照的索引和分块。活动指针先到、索引／分块尚未到齐时，保留上次完整视图并拒绝编辑；活动分块到达后重新加载。新配置的部分数据不会触发默认数据覆盖。
- 未发布的暂存分块仍不触发重载；Web Locks 保护同配置多标签页写入。**这不是跨设备事务或冲突合并实现**：远程修改仍可能与本地发布／旧分块清理交叠，需要真实 Sync 验收，不能承诺多设备同时编辑不丢失。
- 修复 M3 启动竞态：初始化期间改变壁纸设置时，监听器还未注册，页面可能永远显示旧背景。注册监听器后重新读取设置；刷新入口等待初始化完成。M4 原用例可复现超时，修复后通过；另有专门单测。

### WebDAV 与权限

- 按 URI 路径段编码远程目录，支持中文、空格、`#` 和 `%`；解析 XML 使用 DAV namespace，支持任意前缀和省略 resourcetype 的文件条目。
- 列表请求失败／XML 无效会抛错，由现有界面错误提示处理，不再显示为“空列表”。下载超时覆盖响应体读取；中断或超限返回失败。PUT 保留最多两次重试，GET 不自动重试整个备份，用户可在失败后重试。
- 创建目录失败时不继续上传；生成的 OPFS 文件在上传成功或失败后都清理。
- 开发阶段保留 `http://*/*`、`https://*/*`：任意网站图标、用户设置的图片地址与 WebDAV 主机需要跨源访问。扩展无 content scripts，权限用于扩展上下文的请求。仅列出固定图片域名会使自定义服务失效；M4 未加入新的授权弹窗。M5 须结合隐私声明和数据同意流程决定是否将用户域名改为可选授权，并处理 HTTP 正式分发边界。此决定不代表商店审核通过。

具体数据检查：

- 上游导出兼容：取基线 `a706cee56e43b80777de697dd4462083b1f97ef8` 的原始 backup-manager，临时放入**仅供测试的包**，在 Firefox 中导出并用 Ember 恢复。生产包不含这个测试模块。这证明格式／导出器兼容，不能代替 Chrome 实际配置导出的包。
- Ember 自身往返：比较全部 Sync 数据，以及本地图片、图标、图片缓存的记录 ID 与 Blob SHA-256；保留已有 WebDAV 配置并删除恢复前新增的无关 local 标记。
- 六种拒绝场景：重复 ZIP 路径、缺失 Blob、Blob 大小不符、必需记录缺 ID、Sync 单键超额和非 ZIP 内容；均返回失败且原标记／图片快照不变。结构校验没有新增全包密码学认证或 CRC 保证，同大小内容被改写不属于已覆盖场景。
- Firefox 普通导出实际触发下载，等待下载完成后打开 ZIP 检查内容；实际返回 `usedStreaming: false`。WebDAV 备份实际使用 OPFS，清理后临时目录为空。

- 分批写入活动指针、索引、分块，模拟 Sync 的到达顺序：缺块期间阻止编辑并保留视图，到齐后恢复。该测试没有登录账号，不代表真正跨设备同步。
- 本机 WebDAV：连接、两层中文目录、PUT、列表、GET、ZIP 恢复和删除；错误密码、403、响应体停滞和断连均未报告成功。没有宣称坚果云、群晖或其他真实服务已通过。
- 禁用／启用后核对 Sync 标记及 8 MiB Blob 哈希。生命周期脚本的升级包只改测试版本，生产仍为 0.1.0。临时安装重启后需要重新加载，这与正式签名安装的自动加载不同。

### 容量与资源边界

测试图库包括 4 个各 8 MiB 的不可压缩二进制 Blob，共 **32 MiB**，另有小图／缩略图。OPFS 导出后恢复，四条记录的 SHA-256 均一致。它是备份压力样本，不是数千张照片的解码／显示测试。

最新耗时与资源读数以 `firefox-smoke.json` 中 `largeBackup` 为准。采样通过 Windows 进程树仅统计本次 Firefox 与其子进程，约每 500 ms 加系统查询耗时一次；记录的是整个已运行浏览器的工作集基线及观测峰值，**不是备份新增内存或准确瞬时峰值**。本轮基线与峰值可能相同，不能据此推断备份没有内存开销。

本次最终构建样本：ZIP 33,574,082 字节，导出 1,786 ms，导出加恢复及哈希核对共 2,405 ms；工作集基线 1,103,589,376 字节、观测峰值 1,198,886,912 字节，共 4 次采样。单次短样本数据不构成性能承诺。

运行限制：内存导出最多 500 MiB ZIP；恢复输入与解压累计最多 2 GiB、单条目最多 500 MiB、条目数最多 50,000；WebDAV 下载最多 2 GiB且仍在内存拼接。这些是拒绝阈值，不是容量／低内存保证。Firefox 普通下载仍走内存路径，大包需要足够可用内存与磁盘空间，尚未实测 500 MiB 或 2 GiB 边界。

恢复不是跨数据库和 storage 的全局事务。虽然预检查拒绝不会修改正式数据、单个 store 的事务中止会回滚，但如果后续 store／storage 因磁盘、外部写入或强制退出失败，可能已经恢复了前面的 store。错误会返回失败；正式操作前应保留现有备份，失败后重新导入完整备份。没有声称故障中途全局无损回滚。

## 复现

在仓库目录执行（只使用隔离测试配置）：

```powershell
npm ci
npm test
npm run lint
npm run test:firefox-build
npm run build:firefox
npm run lint:firefox
$env:FIREFOX_BINARY = 'D:\Firefox\firefox.exe'
npm run test:firefox:m4
npm run test:firefox:lifecycle
npm run test:firefox:m3
```

M4 脚本需要 Git 中存在上述上游基线；M1 已补全该历史。生命周期测试会在 `.local/m4/` 新建测试 profile，不使用系统默认配置。当前包哈希记录在构建输出、M4 浏览器报告与生命周期报告中；复验时核对三者一致。

本次生产开发 ZIP：100 个文件，4,429,966 字节；SHA-256 `78938eb4f6f30add42fa5a8dd85b003aef28f3a6b620ffafa5d8245f7a3d2475`。M4 安装的是追加上游导出器的测试夹具包，报告中的此哈希标识夹具所基于的生产包；M3 回归和生命周期初始安装使用生产包。
